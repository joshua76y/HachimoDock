# USB 首次配对的无线设备绑定设计

## 意图

设备是受控内网中的辅助终端。无线连接应防止 IP 复用、误连或串板：只有曾经经 USB 真实握手识别过的 ESP32-P4，才可成为桌面端的 TCP 控制目标。此设计不试图抵御局域网攻击或伪造 MAC。

## 范围与约束

- `boardDeviceId` 是固件从 ESP Base MAC 派生的稳定标识；不另存一份格式不同的 MAC，避免双份身份数据漂移。
- 现有 `DeviceBinding` 中的已保存 P4 标识视为历史 USB 配对，保持可用，不要求用户重新插线。
- 一个桌面端可保存多块板；每一块新板都必须先完成一次 USB hello。
- 不修改 P4 固件、TCP JSONL hello、HTTP、音频分片或现有连接时序。
- 不引入密钥、HMAC、额外网络包、连接等待或每包认证。

## 已有行为

USB 自动发现已经会从经过校验的 hello 保存 `boardDeviceId`。无线自动重连会将 IP/端口作为定位信息，使用保存的 `boardDeviceId` 校验 TCP hello，且在候选身份不匹配时不替换现有控制连接。

缺口在于首次设置页仍可在没有既有绑定时直接连 Wi-Fi 并写入新绑定；通用 `save_device_binding` 也可以创建记录。这不满足“先 USB、后无线”的来源约束。

## 方案比较

1. 保持现状：连接快，但首次 Wi-Fi 可直接创建身份记录，不满足规则。
2. **桌面端 USB-first 绑定（采用）**：仅经过原生 USB hello 的连接可创建新绑定；TCP 必须带已有的期望 `boardDeviceId`，只可刷新同一绑定的地址和时间。无线握手维持现状，无额外开销。
3. USB 配对密钥 + 无线挑战响应：可提高抗伪造能力，但超出受控内网辅助终端的风险模型，也会改变协议和恢复流程。

## 行为设计

1. 用户连接一块未绑定 P4 时，桌面端在 USB hello 校验通过后立即持久化该板的 `boardDeviceId`；持久化失败则断开该次 USB 连接并报告错误，避免“看似已配对”的半完成状态。
2. `save_device_binding` 只允许更新已存在的同一 `boardDeviceId`，不得创建新设备身份；它仍可保存该已配对板的 TCP 主机、端口和最后使用时间。
3. `usb_connect_tcp` 必须提供非空、且仍存在于本地绑定记录中的 `expectedBoardDeviceId`；在打开 TCP socket 前完成该检查。TCP hello 与该值不一致时，拒绝候选连接，且不改写绑定。
4. 首次设备设置只提供 USB 配对路径；无已配对设备时，Wi-Fi 提示用户先通过 USB 连接一次。已配对设备仍可在仪表板中填写或更新 Wi-Fi 地址。
5. 解绑继续删除本地记录；若当前正通过该板的 TCP 链路控制设备，立即断开该链路。解绑后无线自动重连和手动无线连接都被拒绝，直到再次 USB 配对。

## 非目标

- 不验证 TCP 客户端身份，不关闭固件 3333/80 端口，也不处理 MAC 伪造或局域网拒绝服务。
- 不修改正在工作的语音传输、草稿确认、摇杆发送/取消，或 Agent 投递逻辑。
- 不改变现有已配对板的无线地址和使用体验。

## 验收与测试

- 新设备无绑定时，直接 TCP 连接与保存新绑定均失败，错误明确要求先 USB 配对。
- USB hello 后会创建绑定；同一板随后可用保存身份建立 TCP，且 hello 不匹配不替换现有连接、不改写绑定。
- 已配对板通过仪表板更新 TCP 地址仍成功；解绑后同一操作被拒绝。
- 运行现有设备设置、绑定和 TCP 身份测试，以及相关 Rust 定向测试；无需新增固件构建或实机烧录。
